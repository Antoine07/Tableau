01 · Comprendre

Que fait Tableau avec les données ?

Dans Tableau, l'étudiant glisse un champ dans une vue ; Tableau calcule les regroupements et interroge la source de données. Sur une base SQL, Tableau peut générer des requêtes SQL. Sur Excel, l'étudiant utilise les mêmes concepts, mais ne saisit pas de requête SQL personnalisée.

Question métier

Quelles catégories génèrent le plus de ventes ? Est-ce également celles qui dégagent le plus de bénéfice ? Quels retours sont associés aux commandes ?

Matériel : Sample Superstore (.xls). Aucun serveur SQL à installer pour les premières manipulations.

04 · Faire le lien avec SQL

SELECT, WHERE et ORDER BY… sans taper de SQL

Dans TableauConcept SQL analogue
Choisir Category et SalesSELECT

Trier les ventes décroissantesORDER BY
-- Requête pédagogique équivalente (pas à coller dans Excel)
SELECT "Category", "Sales"
FROM Orders
WHERE "Region" = 'West'
ORDER BY "Sales" DESC;
  1. Ouvrez Feuille 1. Glissez Category sur Lignes et Sales sur Colonnes.
  2. Glissez Region sur Filtres et sélectionnez une région.
  3. Triez les barres en ordre décroissant.

Nuance : ce SQL est une analogie pédagogique. La requête effectivement produite par Tableau peut différer, notamment parce que la vue agrège les mesures.

05 · Agréger

SUM, GROUP BY et COUNT DISTINCT

Lorsque vous placez Category et SUM(Sales) dans la feuille, Tableau regroupe les ventes par catégorie.

-- Traduction logique de l'analyse
SELECT "Category", SUM("Sales") AS total_ventes,
       SUM("Profit") AS total_benefice
FROM Orders
GROUP BY "Category";
  1. Dans la même feuille, comparez SUM(Sales) et SUM(Profit).
  2. Créez une seconde feuille par région.
  3. Pour compter les clients uniques, utilisez COUNTD(Customer ID) dans Tableau : cela correspond à COUNT(DISTINCT ...) en SQL.

À retenir : ventes élevées ≠ bénéfice élevé. Et COUNT(*) ne compte pas les clients distincts.

Repère facultatif · Une analyse en Tableau, SQL et pandas

Exemple : calculer les ventes par catégorie pour la région West. Les trois écritures partent des mêmes lignes de la table Orders et utilisent la même somme.

TableauSQLpandas
Region → Filtres (West)
Category → Lignes
SUM(Sales) → Colonnes
SELECT Category, SUM(Sales)
FROM Orders
WHERE Region = 'West'
GROUP BY Category;
orders.query('Region == "West"')

Dans pandas, on suppose que orders contient déjà la table Orders et ses colonnes. Les opérations sont comparables, mais le résultat diffère : Tableau construit une vue, SQL renvoie des lignes de résultat et pandas produit un objet tabulaire en mémoire.

06 · Comprendre le modèle

Relation Tableau ou JOIN SQL ?

Les deux mécanismes rapprochent des informations à partir d’une clé, mais ils n’agissent pas au même moment.

Deux niveaux de modélisation
Relation logique TableauJointure physique SQL
Les tables restent séparées dans le modèle logique. Tableau adapte la requête aux champs réellement utilisés dans la vue.Les lignes sont combinées selon une clé et un type de jointure avant l’analyse. Le résultat possède un grain déterminé par cette combinaison.
Approche de départ recommandée pour Orders, Returns et People dans cet exercice.À choisir quand une table combinée est nécessaire et que la cardinalité des clés est comprise.

Exemple : plusieurs lignes de vente pour une commande

Supposons que Orders contienne deux produits pour O-17 (ventes 40 € et 60 €), tandis que Returns contient une ligne O-17 / Yes. Une jointure sur Order ID donne deux lignes, chacune associée à Yes. La somme des ventes reste ici 100 €, car une seule ligne Returns correspond à O-17. Si Returns contenait deux lignes pour O-17, les ventes seraient répétées et totaliseraient à tort 200 €.

SELECT o."Order ID", o."Sales", r."Returned"
FROM Orders AS o
LEFT JOIN Returns AS r
  ON o."Order ID" = r."Order ID";

LEFT JOIN conserve les lignes de gauche sans correspondance ; il ne garantit pas une ligne unique par commande. Avant une jointure physique, vérifiez donc le grain des deux tables et le nombre de correspondances par clé. Une relation logique ne corrige pas les données, mais évite de matérialiser d’emblée une table aplatie.

À retenir : identifiez ce que représente une ligne de chaque table, puis vérifiez si la clé est unique du côté où vous l’attendez.

07 · Exemple métier · Orders + Returns

Formule : part des commandes retournées

Comparer les montants de ventes des commandes retournées renseigne sur les volumes, pas sur la fréquence des retours. Pour comparer des catégories de tailles différentes, on peut rapporter le nombre de commandes associées à un retour au nombre de commandes contenant cette catégorie.

Définition de l’indicateur

Pour chaque catégorie : commandes distinctes retournées ÷ commandes distinctes contenant la catégorie. Il s’agit d’une proportion de commandes, pas du montant de ventes retournées ni du nombre d’articles retournés.

1. Identifier les commandes retournées

Dans la table logique Returns, le champ calculé conserve l’identifiant si un retour est signalé ; sinon il renvoie Null.

// Champ calculé dans Returns
IF [Returned] = "Yes" THEN [Order ID] END

COUNTD ignore les valeurs nulles : seuls les identifiants marqués Yes comptent au numérateur.

2. Former le ratio

// Commande retournée vient de Returns
// Order ID du dénominateur vient de Orders
COUNTD([Commande retournée])
/
COUNTD([Order ID])

Dans Tableau, sélectionnez explicitement le Order ID de la table logique Orders pour le dénominateur. Les deux comptes sont distincts parce que Orders peut contenir plusieurs lignes par commande.

Exemple de lecture · nombres fictifs

Supposons 10 commandes retournées sur 100 pour une catégorie, et 20 sur 400 pour une autre. La seconde compte davantage de commandes retournées en valeur absolue, mais son taux est plus faible : 5 % contre 10 %.

Exemple fictif, indépendant du fichier Superstore

A1010010 ÷ 10010 %
B2040020 ÷ 4005 %

La même définition en SQL

SELECT
    o."Category",
    1.0 * COUNT(DISTINCT CASE
        WHEN r."Returned" = 'Yes' THEN r."Order ID"
    END) / COUNT(DISTINCT o."Order ID") AS order_return_rate
FROM "Orders" AS o
LEFT JOIN "Returns" AS r
    ON o."Order ID" = r."Order ID"
GROUP BY o."Category";

LEFT JOIN conserve les commandes sans correspondance dans Returns pour le dénominateur. CASE choisit les retours pour le numérateur ; COUNT(DISTINCT ...) compte les commandes une seule fois. C’est une traduction pédagogique : on ne colle pas cette requête dans la connexion Excel.

Limite d’interprétation

Le retour est enregistré au niveau de Order ID, pas de la ligne produit. Une commande qui contient plusieurs catégories peut donc contribuer au taux de plusieurs catégories. Cet indicateur ne permet pas d’identifier l’article retourné ni la cause du retour. L’exercice suivant demande de le construire et de l’analyser dans votre fichier.

08 · Comprendre les limites

Où écrire du SQL personnalisé dans Tableau ?

Avec une base de données compatible (par exemple PostgreSQL), Tableau Desktop peut afficher l'option Nouvelle requête SQL personnalisée / New Custom SQL dans la page Source de données.

Important : cette fonction n'est pas disponible sur une connexion Excel moderne. Ne cherchez donc pas ce bouton dans votre fichier Superstore .xls. Pour une vraie manipulation de SQL personnalisé, il faut une base SQL compatible.

Démonstration facultative du formateur

Si une base SQL est disponible, ouvrez une connexion PostgreSQL, choisissez Nouvelle requête SQL personnalisée et saisissez une requête SELECT simple. Sinon, analysez la capture et poursuivez sans blocage.

09 · Appliquer les notions

Exercice d’application — contrôler un taux

Reprenez le modèle logique Orders–Returns et la formule expliquée dans la section précédente. Dans cet exercice, appliquez-la aux catégories de votre fichier et justifiez chaque choix de grain.

  1. Vérifiez les deux relations logiques et repérez dans le volet Données les champs Order ID de Orders et Returns.
  2. Créez Commande retournée dans Returns : IF [Returned] = "Yes" THEN [Order ID] END.
  3. Créez le taux : COUNTD([Commande retournée]) / COUNTD([Order ID]). Pour le dénominateur, choisissez le champ Order ID de Orders.
  4. Construisez une feuille par catégorie. Affichez le taux en pourcentage et placez numérateur et dénominateur dans l’info-bulle.

Questions à résoudre

  1. Quelle catégorie a le taux le plus élevé ? Donnez le taux et les deux effectifs qui le composent.
  2. Le classement en nombre de commandes retournées est-il le même qu’en pourcentage ? Expliquez avec vos résultats.
  3. Pourquoi un filtre Returned = Yes appliqué à toute la vue fausserait-il le dénominateur ?
  4. Pourquoi une commande qui contient deux catégories peut-elle être comptée dans chacune ? Que ne peut-on pas conclure sur le produit effectivement retourné ?
  5. Quel contrôle feriez-vous si le taux dépasse 100 %, si le dénominateur est nul ou si le résultat est vide ?

À produire : une feuille lisible, les effectifs visibles dans l’info-bulle et une conclusion de trois phrases, avec une limite de l’indicateur. Les valeurs dépendent de la version du fichier.

Repère : l’exercice porte sur la proportion de commandes associées à un retour dans chaque catégorie, pas sur la proportion d’articles retournés.
